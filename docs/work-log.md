# 마니또 서비스 작업일지

이 문서는 프로젝트 진행 내용을 날짜순으로 누적한다. 완료된 작업과 아직 구현되지 않은 범위를 구분해 기록하며, 새로운 작업은 문서 하단에 추가한다.

## 2026-09-18 — 서비스 기획

### 목표와 사용자 정의

- 초등학교 교사와 초등학생이 사용하는 반복형 마니또 웹서비스로 범위를 정했다.
- 한 번 매칭하고 끝나는 행사가 아니라, 같은 학급에서 여러 회차를 만들고 지난 활동을 돌아볼 수 있도록 설계했다.
- 교사가 운영하는 **방장 서비스**와 학생이 참여하는 **회원 서비스**를 분리했다.
- 서비스 분위기는 초등학생이 부담 없이 접근할 수 있는 귀엽고 장난스러운 방향으로 정했다.

### 핵심 운영 흐름

- 교사: 학급 생성 → 학생 명단 등록 → 회차 생성 → 매칭 실행 → 미션 운영 → 도움 요청·메시지 확인 → 정체 공개 → 회고
- 학생: 입장 카드 로그인 → 자신의 마니또 확인 → 미션 수행 → 익명 쪽지·응원 → 도움 요청 → 정체 공개 → 회고
- 반복 참여를 위해 학급과 회차를 분리하고, 한 학급에 여러 회차가 누적되는 구조를 채택했다.
- 초등학생 대상 서비스라는 점을 반영해 교사 통제, 최소 개인정보, 익명 상호작용 검토, 신고·도움 요청 기능을 기획에 포함했다.

## 2026-09-21 — Firebase 백엔드 설계 및 구현

### Firestore 데이터 구조

- 교사, 학급, 학생, 회차, 매칭, 미션, 메시지, 도움 요청, 감사 카드, 감사 로그를 표현하는 Firestore 경로와 데이터 계약을 설계했다.
- 클라이언트가 매칭 결과나 권한 데이터를 임의로 바꾸지 못하도록 중요한 쓰기는 Cloud Functions만 수행하게 했다.
- 학급과 회차를 분리해 같은 학급에서 여러 번 마니또 활동을 진행할 수 있도록 했다.
- 교사 대시보드와 학생 화면에서 필요한 복합 인덱스 5개를 정의했다.

### 보안 규칙

- 교사는 자신이 담당하는 학급의 운영 데이터만 읽도록 제한했다.
- 학생은 자신이 속한 학급·회차에서 허용된 데이터만 읽도록 제한했다.
- 학생에게 자신의 대상자만 공개하고 전체 매칭표는 직접 조회할 수 없도록 설계했다.
- 클라이언트의 직접 쓰기를 기본 차단하고 서버 함수에서 검증된 요청만 처리하도록 했다.
- 입장 카드 재발급 시 `sessionVersion`을 증가시켜 기존 학생 세션을 무효화하도록 했다.

### Cloud Functions

다음 Callable Function 4개를 TypeScript로 구현했다.

- `createClass`: 확인된 교사가 새 학급을 생성
- `registerStudents`: 학급에 학생을 일괄 등록하고 입장 카드 발급
- `loginStudent`: 학급 코드와 입장 카드 검증 후 Firebase Custom Token 발급
- `rotateStudentCredential`: 분실·노출된 학생 입장 카드를 교사가 재발급

학생 입장 카드의 원문은 저장하지 않고 salt가 포함된 scrypt 해시만 저장한다. 운영 환경의 Callable Function에는 App Check 검증을 적용하고, Emulator에서만 이를 해제했다.

### 검증

- TypeScript 빌드 통과
- 입장 코드 관련 단위 테스트 4개 통과
- Firestore 보안 규칙 테스트 8개 통과
- 통합 흐름 테스트 1개 통과
  - 교사 학급 생성
  - 학생 등록
  - 학생 로그인
  - 학생의 직접 쓰기 차단
  - 카드 재발급 후 기존 카드와 세션 무효화
  - 새 카드 로그인 성공

### 배포 준비

- Firebase Emulator 구성을 추가했다.
- 실제 프로젝트 오배포를 막기 위해 프로젝트 ID를 두 번 확인하는 `scripts/deploy-backend.mjs`를 만들었다.
- Firestore와 Functions 배포 절차, 서울 리전 선택, App Check·교사 인증 요구사항을 문서화했다.
- `.firebaserc`의 기본 프로젝트 `demo-manitto`는 로컬 Emulator 전용으로 유지했다.

## 2026-09-27 — 학생 카드 재출력·시즌 설정 UX 개편

- 사용자 요청의 카드 최초 재방문 출력 불가, 재발급 뒤 인쇄 단절, 23명 목록의 과밀한 버튼, `회차` 용어와 시각 입력 문제를 확인했다. [6개 가상 전문가의 사전·구현 후 검토](design-reviews/2026-09-27-cards-and-seasons.md)를 기록했다. 외부 전문가 참여는 아니다.

## 2026-09-28 — 시즌 준비·미션·쪽지 대화·학생 카드 개선

- [6개 가상 전문가 역할의 사전·구현 후 검토](design-reviews/2026-09-28-season-missions-messages-cards.md)를 기록했다. 실제 외부 전문가나 교사·학생 관찰은 아니다. 시즌 준비는 기본 정보·참가자·미션·쪽지·확인/저장 5단계로 나누고, 기본 정보의 수업일 개별 입력을 제거해 시작/종료일에서 평일을 자동 선택한다. 확인 화면은 길게 나열한 날짜 대신 카드형 요약으로 바꿨다.

## 2026-09-28 — 진행 중 친구 이름 비공개 보강

- 미확인: 실제 아동·교사 사용성 관찰, 200% 확대·VoiceOver, 공개 시즌에서 새 진행 시즌으로 즉시 전환되는 순간의 수동 브라우저 재현. 자유 쪽지 문장만으로 상대를 추측할 가능성은 UI 비공개와 별도로 운영상 확인해야 한다.

## 2026-09-28 — 입장 카드 접속 QR 추가

- 사용자 지적으로 입장 카드 인쇄물에 QR이 전혀 없던 누락을 확인했다. 계획서 §6.4의 공통 접속 QR 원칙에 따라 전체·선택·재발급 인쇄 경로에 동일 사이트 `/student` QR을 추가했다. QR에는 학생 이름·학급/개인 코드·학생 ID를 넣지 않는다. 스캔 후 학생은 카드에 인쇄된 두 코드를 직접 입력한다. QR을 못 쓸 때는 인쇄된 주소로 들어갈 수 있다.
- QR 생성·이미지 디코딩을 마친 뒤에만 인쇄를 연다. 실패하면 빈 QR 카드를 출력하지 않고 재시도 오류를 표시한다. 기존 인쇄 종료/시간 초과/교사 화면 이동 경로에서 카드 원문과 QR 인쇄 DOM을 함께 정리한다. [6개 가상 전문가 관점 사전·사후 검토](design-reviews/2026-09-28-entry-card-qr.md)를 수행했으며 실제 외부 전문가 참여는 아니다.
- 전체 빌드, 함수 단위 10건, Firestore Rules 13건, 두 시즌·40명 통합 3건, QR 생성·해독 시험 1건과 `git diff --check`를 통과했다. Chromium A4 인쇄에서 가상 2명의 정상·긴 이름 카드를 육안으로 확인했고 PDF 첫 장의 QR을 120dpi 래스터 이미지에서 다시 해독했다. 가상 40장 인쇄 PDF는 정확히 A4 40쪽이었다.
- GitHub `main` 커밋 `180ca3b` 푸시와 해당 커밋의 Vercel `success`를 확인했다. Firebase 함수/Rules는 이번 웹 전용 변경으로 재배포하지 않았다. 배포 웹에서 승인 교사의 가상 4명 학급 전체 출력 버튼을 실행해 QR 이미지 4개 로드와 `/student` 주소, 다른 메뉴 이동 후 인쇄 DOM 0개, 브라우저 콘솔 오류 0건을 확인했다.
- 실제 종이 인쇄와 휴대전화 카메라 스캔, 선택·재발급 QR의 별도 브라우저 인쇄, QR 생성 실패 UI 수동 재현은 미확인이다. 실제 카드 비밀이 들어간 스크린샷·PDF는 저장하지 않았다.

## 2026-09-28 — 학생 쪽지 두 관계 대화 분리

- 사용자 보고를 조사한 결과, 서버가 첫 쪽지·답장 한 건을 두 학생에게 동시에 전달하는 로직은 없었다. 받은/보낸/작성 탭이 서로 다른 두 관계의 기록을 섞어 보여 수신자를 오해할 수 있었다. [여섯 가상 전문가 관점의 설계·검증 기록](design-reviews/2026-09-28-two-student-mail-conversations.md)에 근거를 남겼다. 실제 외부 전문가 검토나 학생 관찰은 아니다.
- 학생 우편함을 `내가 맡은 친구`와 `나를 맡은 친구`의 두 대화로 나눴다. 첫 쪽지의 자기 송·수신 방향을 답장 체인에 상속해 기존 기록도 분류한다. 같은 학생이 두 역할에 해당하더라도 두 대화가 섞이지 않는다. 분류 불명인 기록은 별도 읽기 영역에 두고 그 기록을 답장 대상으로 삼지 않는다.
- 첫 대화의 새 쪽지는 서버 배정 상대 한 명에게, 둘째 대화의 작성은 그 방향으로 실제 받은 쪽지의 발신자 한 명에게 보내도록 기존 서버 제한을 유지한다. 역할별 초안을 따로 보관하며 친구 이름·UID를 학생에게 더 보내지 않는다. 숨김·신고·교사 모니터링을 유지한다.
- TypeScript/Vite 전체 빌드, 함수 단위 12건, 두 시즌·40명 통합 3건, Firestore Rules 13건과 `git diff --check`가 통과했다. 통합 시험에서 실제 단일 수신·양방향 분류·답장 상속·타 학생 답장 거절을 확인했다.
- Firebase 개발 프로젝트 `manito-938cc`의 `getStudentActivity` 함수 업데이트가 성공했다. GitHub/Vercel 웹 배포와 브라우저 사후 검증은 뒤에 구분해 기록한다.
- 코드·문서 커밋 `d9a079e`을 GitHub `main`에 푸시했고 해당 커밋의 Vercel 배포 상태가 `success`임을 확인했다. Firebase 함수 배포, GitHub 푸시, Vercel 웹 배포를 각각 확인했다.
- 배포 웹의 로그인 화면 로드를 확인했다. 이전 교사·학생 브라우저 인증이 만료됐고 이 브라우저 세션에서는 교사 Google 로그인이 완료되지 않아 가상 입장 카드로 학생 화면에 재입장하지 못했다. 따라서 실제 배포 화면의 두 탭, 긴 문장, 320·360·390·768·1280px, 키보드·초점 검증은 미완료다. [사후 검토 기록](design-reviews/2026-09-28-two-student-mail-conversations.md)에 여섯 관점의 확인 범위와 제한을 분리해 남겼다.

## 2026-09-28 — 교사 학생별 상태 확인

## 2026-09-29 — 교사·학생 로그인 오류 진단·수정 및 교사 자동 승인 전환

- 배포 웹(`manito-one-blond.vercel.app`)에서 교사 Google 로그인이 실패하던 4가지 원인을 확인하고 수정했다. [6개 가상 전문가 관점의 사전·사후 검토](design-reviews/2026-09-29-teacher-login-fix.md)를 기록했다. 실제 외부 전문가나 교사 과업 관찰은 아니다.
  1. **데스크톱 팝업 차단(`auth/popup-blocked`)**: `@firebase/auth`의 `BrowserPopupRedirectResolver`가 데스크톱에서 페이지 로드 시점이 아니라 클릭 시점에 `gapi.iframes` 스크립트와 `/__/auth/iframe`을 비동기 초기화한 뒤 `window.open()`을 호출해 브라우저 사용자 제스처 활성 시간이 만료되던 문제를 해결하기 위해 `initializeAuth` 전에 `_shouldInitProactively = true`를 설정해 페이지 로드 시점에 미리 준비하도록 했다.
  2. **현재 창 리다이렉트 대체 수단 및 교사 세션 유지**: 팝업이 차단되거나 열리지 않는 환경을 위해 교사 로그인 시 `browserSessionPersistence`를 적용하고 `"팝업이 안 열리면 현재 창에서 로그인"`(`signInWithRedirect`) 보조 버튼과 `getRedirectResult` 오류 복구를 추가했다. 학생 로그인(`studentLogin`)과 로그아웃(`logout`)은 공용기기 보호를 위해 기존대로 `inMemoryPersistence`로 즉시 전환한다.
  3. **교사 계정 자동 승인(`verified`) 전환**: 운영자 수동 CLI 승인 없이는 신규 Google 계정이 `pending`에 머물러 학급을 만들 수 없던 구조를 사용자 요청에 맞춰 변경했다. `ensureVerifiedTeacherAccount`와 `requireVerifiedTeacher`에서 정지(`suspended`)되지 않은 교사 계정을 첫 로그인/호출 시 자동으로 `verified` 저장 및 Custom Claims(`role: "teacher", teacherVerified: true`) 부여하도록 수정했고, 클라이언트 `loadTeacher`는 클레임 미반영 시 `getIdToken(true)`로 토큰을 즉시 갱신해 Firestore Security Rules(`isTeacher()`)가 바로 통과되도록 했다.
  4. **인증 콜백 오류 메시지 증발 수정**: `onAuthStateChanged` 내 오류 발생 시 `exit()`(`signOut`) 호출이 재귀적으로 `onAuthStateChanged(null)`을 발생시켜 `setError("")`로 오류 배너를 지우던 경쟁 상태를 `preserveErrorOnSignOut` 플래그로 수정하고 팝업 차단·취소·네트워크 오류의 한국어 안내를 보강했다.
- 학생 로그인(`loginStudent`)은 개발 클라우드(`manito-938cc`) 함수 로그와 Custom Token 서명 경로를 점검해 정상 동작 상태임을 확인했다.
- `npm run build`(Functions·Web TypeScript 및 Vite 빌드), 함수 단위 테스트 12건, QR 단위 테스트 1건, `git diff --check`가 통과했다. 로컬 환경에 Java Runtime이 설치되어 있지 않아 Firestore Emulator 통합·Rules 테스트는 이번 세션에서 실행하지 못했다(코드에는 자동 승인 통합 테스트 반영 완료).
- Firebase 개발 프로젝트 `manito-938cc`(`asia-northeast3`)에 변경된 백엔드 함수(`getTeacherStatus`, `listClasses`, `createClass`)를 배포 완료했다. GitHub `main` 푸시 및 Vercel 프런트엔드 배포와 구분해 기록한다.
- 남은 확인: 배포된 Vercel 웹에서 실제 교사 Google 계정 클릭 시 팝업/현재 창 로그인과 첫 학급 생성 전체 흐름, 로컬 JDK 설치 환경에서의 Emulator 통합 테스트 재실행.

- 게임 분위기만 독자적인 CSS/SVG 풍경과 캐릭터로 구현했다. 점수·재화·레벨·순위·접속 보상은 추가하지 않았다. 마니또 API와 데이터 계약은 바꾸지 않았다.
- [6개 가상 전문가 프로파일의 사전·사후 검토](design-reviews/2026-10-30-pixel-world-login-and-map.md)를 기록했다. 로컬 브라우저에서 로그인 폼(390px), 월드(360·390·768·1280px), 키보드 이동, 모바일 방향 버튼 이동/자동 추적, 접근성 트리의 장소 및 로그인 컨트롤 이름을 확인했다. 실제 로그인 데이터는 입력하지 않았다.

## 2026-10-30 — 두 서브 에이전트로 서비스 이름 제안과 도트 이미지 로그인 구현

- `image_gen`으로 독자적인 픽셀 마을·학교 건물·캐릭터·우체통·게시판 풍경을 생성하고, 로컬 에셋 `web/src/assets/student-login-world.webp`(1672×941px, 약 407KB)로 연결했다. 이미지 속 UI를 조작하는 방식이 아니라 실제 HTML 로그인 폼을 이미지 앞의 불투명 카드에 배치했다.

- [6개 가상 전문가 관점의 사전·사후 검토](design-reviews/2026-10-30-pixel-image-login.md)를 기록했다. 서브 에이전트는 IAB의 320·360·390·768·1280px 화면, 입력 라벨, 코드 보기/가리기, 체크박스 안내, Tab 초점을 검토했다. 부모 에이전트는 React 품질 스킬 기준으로 props/상태/인증 연결·로컬 이미지 로딩·접근성 경계를 검토했다.
- 최종 WebP 에셋 기준 웹 빌드와 `git diff --check` 통과를 서브 에이전트 보고로 확인했고, 부모가 통합 문서 추가 후 `git diff --check`를 다시 통과했다. 실제 카드 제출·Firebase 로그인, 화면 읽기 도구, 200% 글자 확대, 실기기 터치·학생 이해도는 미확인이다. 배포하지 않았다.

## 2026-10-30 — 현재 우리 반 월드 화면 미리보기 제공

## 2026-10-30 — 월드의 평면 도형 시안을 실제 도트 마을·캐릭터로 교정

- 사용자가 승인한 도트 로그인과 초기 월드의 시각 품질이 다르다는 지적을 반영했다. `StudentClassroom`의 SVG 풍경과 CSS 얼굴을 제거하고, 로그인 이미지를 스타일 참조로 새로 생성한 실제 픽셀 마을과 투명 캐릭터 에셋을 사용한다.
- 맵은 `web/src/assets/world-town-v2.webp`(1774×887, 약 574KB), 캐릭터는 `web/src/assets/world-avatar-v2.webp`(1333×1180, RGBA 약 329KB)로 저장했다. 생성 원본은 보존했으며 프롬프트·출력 경로는 [6개 관점 검토 기록](design-reviews/2026-10-30-world-raster-art-correction.md)에 남겼다.
- 학교·정원·우체국·게시판에 간결한 표지를 배치해 풍경을 드러냈다. 캐릭터는 실제 이미지로 좌우 이동·방향 전환하고, 장소 근처의 ‘들어가기’/Enter로 기존 목적지에 진입한다. 직접 표지 클릭도 유지했다. 오늘 할 일 URL과 로그인 화면은 유지한다.
- IAB 기본/1280/768/390/360px의 실제 화면, 방향 버튼으로 16%→40% 이동·주변 장소 변경, 키보드 Tab/방향키·Enter, 예시 내부 기능 콜백을 확인했다. 모바일에서는 지도 안에서만 가로 이동하고 캐릭터를 따라간다. 실제 학생 데이터 변경은 하지 않았다.
- 신규 `student-world.css`를 메인과 미리보기에 연결했다. 타이머/resize 이벤트 정리, 이미지 alt와 입장 목적지 이름, 주요 48px 컨트롤, reduced-motion을 코드에서 확인했다. 실제 학생·실기기·화면 읽기·200% 확대·Firebase 실세션은 미확인이다. 배포하지 않았다.
- 최종 `web/npm run build`와 `git diff --check`를 통과했다. Vite의 기존 큰 JS 번들 경고는 유지된다. 수정된 도트 월드 미리보기를 기본 화면 폭과 초기 캐릭터 위치로 열어 두었다.

## 2026-10-30 — 캐릭터 이동 후 건물 상호작용과 실제 페이지 전환 연결

- 사용자의 명시 요청에 맞춰 원거리 표지의 즉시 진입을 제거했다. 길/먼 건물을 선택하면 캐릭터가 해당 위치로 걸어가고, 도착 후 건물 그림 클릭·‘상호작용’ 버튼·E/Enter로 페이지에 들어간다. 모든 진입 경로에 같은 근접/정지 조건을 적용했다.
- `useWorldMovement.ts`로 연속 이동을 분리했다. 방향키/A·D와 화면 방향 버튼은 누르고 있는 동안 이동하고 해제하면 멈춘다. 포인터 취소·창 비활성화·컴포넌트 해제에서 RAF와 입력 상태를 정리한다. 생성된 도트 맵·캐릭터 이미지는 그대로 사용한다.
- 실제 App에서는 기존 학생 페이지와 오늘 할 일 URL을 유지했다. 마을 복귀 위치는 현재 입장의 메모리에 보존하고 로그아웃/학생 전환 시 초기화한다. API·데이터 계약 변경은 없다.
- 로컬 미리보기는 안내문만 바꾸던 방식을 없애고 `?place=missions|mail|community`에 따라 별도 예시 페이지를 연다. 페이지 제목 초점·브라우저 뒤로가기·마을 복귀와 위치 보존을 제공한다. 예시 페이지는 실제 학생 API를 호출하지 않는다.
- [6개 관점 검토 및 전체 흐름 검증](design-reviews/2026-10-30-world-object-interaction.md): 실제 건물 그림 클릭으로 미션 페이지, 키보드 연속 이동 후 E로 우편함, 모바일 방향 버튼/상호작용으로 게시판 전환을 확인했다. 원거리 선택 시 URL 유지, 이동 중/비근접 상호작용 비활성, 길 클릭 이동, 복귀 위치, 360/390/768/1280px 화면과 브라우저 오류 없음도 확인했다.
- 실제 Firebase 실세션·학생 사용성·화면 읽기·200% 확대·실기기 터치는 미확인이다. 배포하지 않았다.
- 최종 웹 빌드, 미리보기 TSX 별도 TypeScript 검사, `git diff --check`를 통과했다. 기존 Vite JS 번들 크기 경고는 유지된다.

## 2026-10-30 — 구역 표지·걷기 바로가기·최상단 타이틀바 제거
