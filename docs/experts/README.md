# 서비스 디자인 전문가 검토 지침

작성일: 2026-09-27

잘 구성되고 아름다우며 쉽게 조작할 수 있는 서비스를 만들기 위한 6개의 전문가 프로파일이다. 모두 휴리스틱을 이해하고, 취향을 말하는 데서 끝내지 않고 사용자 과업과 관찰 근거로 판단한다. **가상의 전문 역할 정의**이며 실존 인물의 이력·자격이나 외부 자문 계약을 뜻하지 않는다.

## 전문가 구성

| 분야 | ID · 프로파일 | 중심 질문 | 주 산출물 |
|---|---|---|---|

| 웹디자인 | [WD-02 · 반응형 레이아웃과 타이포그래피](wd-02-responsive-layout.md) | 화면 크기와 콘텐츠 길이가 달라져도 구성이 유지되는가? | 화면별 배치·줄바꿈·밀도 규칙 |
| UX | [UX-01 · 정보 구조와 과업 흐름](ux-01-information-architecture.md) | 사용자가 원하는 일을 올바른 위치에서 끝낼 수 있는가? | 사이트맵·페이지/섹션 구분·과업 흐름 |

WD는 화면의 인상과 공간, UX는 과업과 이해, UI는 조작과 구현 상태에 최종 의견을 낸다. 중복 발견은 하나의 문제 ID로 묶되 각 관점의 근거를 유지한다. 누구도 다른 관점의 검토를 대신 통과시키지 않는다.

## 공통 휴리스틱

다음 H1~H10은 [Jakob Nielsen의 10가지 사용성 휴리스틱](https://www.nngroup.com/articles/ten-usability-heuristics/)을 짧게 정리한 참조표다. 각 프로파일은 전체를 공통 기반으로 사용하고 자신의 전문 영역을 더 깊게 검토한다.

| ID | 기준 |
|---|---|
| H1 | 현재 상태와 동작 결과를 알 수 있다. |
| H2 | 사용자의 언어와 실제 업무 순서에 맞는다. |
| H3 | 취소·뒤로가기·복구 등 통제 수단이 있다. |
| H4 | 용어와 동작이 일관되고 익숙한 관례를 따른다. |
| H5 | 잘못된 입력과 실수를 미리 줄인다. |
| H6 | 외워서 조작하기보다 보고 알아볼 수 있다. |
| H7 | 처음과 반복 사용 모두 효율적이다. |
| H8 | 필요한 정보가 명확하고 불필요한 경쟁 요소가 적다. |
| H9 | 오류 원인과 회복 방법을 이해할 수 있다. |
| H10 | 필요한 위치에서 도움을 찾을 수 있다. |

추가로 관련 요소의 근접·정렬·그룹화, 선택의 부담, 누르기 쉬운 목표 크기, 단계적 정보 제공을 설계 관점으로 사용한다. 특정 법칙의 이름만으로 메뉴 수나 클릭 수를 기계적으로 정하지 않는다. 아래 수치와 절차는 별도 표기가 없는 한 이 프로젝트의 설계·검증 기준이다.

## 개발 착수 절차

1. **검토 준비:** 사용자와 핵심 과업, 변경 이유, 현재 문제 증거, 페이지/섹션 구성도, 화면 스케치 또는 구체적인 배치 명세를 준비한다. 기존 서비스는 해당 화면과 코드도 확인한다. 새 서비스는 사용자 시나리오를 기준으로 평가한다.
2. **6개 관점의 개별 검토:** 같은 자료를 각 프로파일로 검토하고 개별 결과를 먼저 기록한다. 실제 참여자 또는 에이전트와 역할 기반 검토 여부를 밝힌다. 도구·사람이 6개 있지 않아도 검토를 수행할 수 있으나, 독립적인 인간 전문가 6명의 자문으로 표현하지 않는다.
3. **문제 통합과 설계 수정:** 발견 위치·발생 조건·휴리스틱·영향·심각도·수정안·검증 방법을 정리한다. 미적 선호가 충돌하면 두 안을 비교하고 읽기·발견·조작에 미치는 영향으로 선택 이유를 남긴다.
4. **사전 통과:** 6개 관점이 모두 `통과`이고 미해결 P0·P1이 없어야 개발 코드를 작성·수정한다. `수정 필요` 또는 `근거 부족`인 관점은 자료와 설계를 보완해 재검토한다. P2·P3는 담당 역할·처리 시점·확인 방법을 정한다.
5. **구현과 재검토:** 통과한 설계대로 구현하고 실제 브라우저 증거로 같은 6개 관점을 재검토한다. 페이지 구조·핵심 조작·데이터 노출 등 중요한 설계가 바뀌면 해당 코드 구현 전에 6개 관점의 사전 검토를 갱신한다.
6. **완료 기록:** 검증 환경, 실제 결과, 해결 여부와 남은 항목을 기록한다. 문서·작업일지와 연결하고 배포 검증은 로컬 검증과 구분한다.

작업별 기록은 [양식](review-template.md)을 복사해 `docs/design-reviews/YYYY-MM-DD-작업명.md`로 만든다. 영향이 적은 변경은 각 관점의 판단과 근거를 한두 문장으로 작성해도 되지만 검토 자체를 생략하지 않는다. 순수 서버 변경은 사용자 상태·오류·대기·권한 노출에 영향이 없는지 각 관점으로 확인한 뒤 관련 없는 화면 검증만 `해당 없음 + 근거`로 표시한다. 문서 작성과 조사에는 서비스 개발 검토를 먼저 요구하지 않는다.

## 심각도와 판정

발생 빈도·피해·회피 가능성을 함께 고려한다. 아래 P0~P3는 프로젝트 자체 우선순위이며 Nielsen의 0~4 평가 척도와 동일한 척도가 아니다. 평가 방식 참고: [사용성 문제의 심각도](https://www.nngroup.com/articles/how-to-rate-the-severity-of-usability-problems/).

| 등급 | 판단 기준 | 처리 |
|---|---|---|
| P0 · 치명적 | 민감 정보 노출, 의도치 않은 삭제·공개, 핵심 과업 전체 차단 | 사전 설계에서 해결 전 착수 금지; 구현에서 발견하면 완료·배포 금지 |
| P1 · 중대 | 주요 동작을 찾거나 수행하기 어려움, 겹침·잘림 때문에 선택을 오해함, 핵심 키보드 경로 차단 | 수정·재검토 전 착수 또는 완료·배포 금지 |
| P2 · 보통 | 수행할 수 있으나 반복 혼란·불필요한 이동·오류를 유발함 | 설계 단계에 수정 계획 확정; 변경 범위의 P2는 완료 전에 해결 |
| P3 · 경미 | 과업을 방해하지 않는 시각적 불균형·작은 일관성 결함 | 수정하거나 사유·담당·후속 시점을 기록 |

개별 판정은 `통과 / 수정 필요 / 근거 부족`이다. 기존 시스템의 범위 밖 P2를 남길 때는 영향과 후속 작업을 명시하며, 현재 변경의 P2를 범위 밖으로 돌려 완료 처리하지 않는다. P0·P1을 다른 관점의 좋은 점수로 상쇄하지 않는다. 보지 못한 화면·실행하지 않은 시나리오는 `미확인`이며 통과로 계산하지 않는다.

## 구현 후 공통 확인 기준

- **정보 구조와 영역 구분(Surface Hierarchy):** 각 페이지의 목적과 주요 행동, 메뉴의 현재 위치, 관련 섹션의 제목과 경계를 확인한다. **배경 캔버스(Layer 0) · 상단 헤더/탐색 크롬(Layer 1) · 일반 섹션 카드(Layer 2) · 1순위 핵심 스포트라이트(Layer 3)**가 배경색·테두리·그림자·간격으로 분명히 구분되어야 하며, 배경 위에 글자나 버튼이 영역 없이 떠 있는 인상을 주지 않는다.
- **1초 초점(Focal Point)과 시각 위계:** 화면을 열었을 때 1초 안에 가장 중요한 핵심 포인트(예: 입장 카드 입력과 입장하기 버튼, 오늘 해볼 미션과 해냈어요 버튼, 교사 운영 요약의 긴급 도움 요청·현재 시즌 상태)가 한눈에 들어오는지 확인한다. 하나의 흰 패널 안에 성격이 다른 정보를 평면 줄글로 합쳐 핵심 포인트를 묻어버리지 않는다.
- **컨트롤 역할 분리:** 탭/세그먼트 전환(트랙형 스위치), 필터 칩, 주 실행 버튼(Primary CTA), 보조 버튼(Secondary/Outline), 위험 행동(Danger), 상태 배지(Badge)의 모양과 색이 서로 구분되어야 한다. 모든 버튼을 동일한 벽돌색/테두리 버튼으로 통일해 시각 경쟁을 일으키지 않는다.
- **반응형과 첫 화면(Fold) 밀도:** 기본 확인 폭은 360·390·768·1280px이며, 320 CSS px 상당의 좁은 화면에서도 핵심 내용의 재배치를 확인한다. **모바일(390×844px)에서 과도한 장식 제목이나 중복 배지 때문에 핵심 입력·주 행동 버튼이 화면 밖으로 밀려나지 않는지** 확인한다. 글자 확대 200%, 긴 문장·이름, 빈 목록·최대 항목 수를 포함한다.
- **레이아웃:** 라벨과 조작 요소가 같은 그룹으로 보이고 긴 선택지가 서로 겹치지 않아야 한다. 불필요한 페이지 전체 가로 스크롤, 글자 잘림, 한글 음수 자간 뭉침, 과도한 공백, 소속 섹션 없이 바닥에 흩어진 고립 버튼이 없어야 한다.
- **조작 상태:** 기본·초점·선택·비활성·처리 중·성공·오류·빈 상태를 확인한다. 저장 범위와 결과, 뒤로가기·취소·재시도, 중복 입력 방지, 페이지 이동 후 초점을 확인한다.
- **접근성:** 의미 있는 제목·라벨, 키보드 순서와 보이는 초점, 색 이외의 상태 구분, 대비, 화면 읽기 도구의 이름·역할·상태를 검토한다. WCAG 2.2 AA를 목표로 삼되 일부 체크 통과만으로 전체 준수를 주장하지 않는다.
- **측정 기준:** 일반 텍스트 대비 4.5:1 이상을 기본 목표로 한다. 주요 버튼·선택 행의 터치 영역은 이 프로젝트에서 44×44 CSS px 이상, 학생의 주요 조작은 48×48 이상을 목표로 한다. 체크박스 그림 자체를 확대하기보다 연결된 라벨을 포함한 클릭 영역을 확보한다.
- **증거:** 화면 크기·브라우저·경로·상태·재현 순서·결과를 적는다. 가로 넘침(`scrollWidth <= clientWidth`) 수치만으로 통과 처리하지 않고 실제 렌더링 캡처로 영역 분리·초점 가시성을 함께 검증한다. 가상 데이터만 사용하고 스크린샷·URL·로그에 학생 정보나 카드 코드를 남기지 않는다.

좁은 화면 검토는 [W3C Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html), 대비는 [Contrast (Minimum)](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)을 참고한다. WCAG 2.2 AA의 [Target Size (Minimum)](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)은 예외를 포함한 24×24 CSS px 기준이다. 위 44·48px는 아동과 터치 조작을 고려해 더 크게 정한 자체 목표이며 AA의 최소 수치로 인용하지 않는다.

## 마니또 서비스에서 우선 검토할 과제

사용자는 2026-09-27에 한 페이지에 기능이 몰린 구성과 선택 목록의 화면 깨짐을 지적했고, **2026-09-29에 이전 디자인 수정 이후에도 영역 구분이 제대로 되지 않고 화면에서 가장 중요한 포인트가 한눈에 들어오지 않는 문제**를 다시 지적했다. 다음 UI 수정은 이 문제를 검토 입력에 반드시 포함한다.

- **상단 헤더·탐색 바·문맥 헤더·본문 카드·스포트라이트 영역**의 표면 계층을 분리해 어디가 메뉴이고 어디가 핵심 작업 영역인지 즉시 구분되게 한다.
- **학생 화면:** 홈에서 ‘시즌 상태/내 기록 요약 타일’과 **‘오늘 해볼 미션 스포트라이트 카드(주 행동: 해냈어요)’**를 시각적으로 명확히 분리·강조하고, 미션 화면의 상태 탭/범주 칩·미션 카드 배지, 우편함의 대화방 배경·말풍선·작성 영역을 한눈에 구분되게 한다.
- **교사 화면:** 학급 문맥 바·좌측/상단 메뉴·활성 시즌 배너·긴급 안전/도움 요청 카드·단계별 시즌 설정·상태 확인 워크스페이스의 영역 경계와 정보 위계를 분명히 세운다.
- **입장(로그인) 화면:** 중복 배지와 과도하게 큰 영웅(Hero) 여백을 줄이고, 서비스 전환 세그먼트 바와 입장 카드 폼이 모바일 첫 화면(390×844px)에 한눈에 들어오도록 구성한다.
- 전문가 검토는 실제 교사·학생 사용성 시험과 보안·개인정보 검토를 대신하지 않는다.
