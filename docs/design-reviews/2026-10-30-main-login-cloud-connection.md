# 전문가 검토 기록: 현재5173 학생 로그인의 기존 개발DB 연결 복구

## 요구·설계·수행

2026-10-30 사용자가 현재5173/student에서 로그인이 안 된다고 재보고했다. `/root`가 직접 여섯 가상 프로파일을 적용하며 외부 전문가 검토가 아니다. 전문가 운영 지침/여섯 프로파일과 오늘 할 일 실제연동 검토를 참조한다.

원인: 현재5173 Vite가 기존 .env.local의 Emulator=true/demo-manitto를 읽고 있지만9099/8080/5001 리스너가 없다. 동일 repo의 git제외 .env.cloud.local은 기존 개발프로젝트 manito-938cc와 Emulator=false를 제공한다. 카드/DB가 잘못됐다는 근거는 없다.

조치: 기존 env.local과 DB·카드·loginStudent·CustomToken 검증을 바꾸지 않고5173만 cloud모드의 고정빌드로 제공한다. 사용자 입력 중 병렬 main수정의 HMR로 재로딩되는 문제도 피한다. index와 기존 world preview를 함께 빌드해 두 탭의 경로를 보존한다. 기존 개발 Firebase대상만 사용하고 운영배포/새 접근권한은 만들지 않는다. 본인 카드 재입력·로그인 성공은 사용자 실제조작이나 이미 인증된 세션으로만 확인하며 자격을 임의로 추측/조회하지 않는다.

## 구현·검증

- 기존5173 Emulator Vite를 종료하고, cloud guard를 통과한 index/world 두 진입점의 고정빌드를 `/private/tmp/manitto-main-cloud-preview-20261030`에 생성해 같은5173에서 제공했다. 소스·env.local·DB·카드·배포는 변경하지 않았다. cloud설정 파일은 git제외 상태임을 확인했다.
- 빌드의 전체JS자산에서 기존 manito-938cc는 있고 demo-manitto 및 명시적 로컬Auth9099주소는 없음을 확인했다. 첫 검사에서 app청크만 보면 공통Firebase코드가 다른청크에 있어 projectID검출이 안 됐고, 전체청크 검사로 바로잡았다. 포트숫자 문자열만으로는 SDK내부값과 연결대상을 구분하지 않으므로 이를 Emulator연결 증거로 사용하지 않았다.
- 현재 사용자7번탭의5173/student를 새로고침해 실제 cloud고정빌드 `/assets/app-DdIgGtDQ.js` 로드, 학급/카드입력과 입장버튼, 즉시오류없음을 확인했다. 사용자 자격은 입력/조회하지 않았다. 빈 로그인화면 증거는 `assets/main-login-cloud-connection-2026-10-30.png`다.
- 기존개발 loginStudent에 학생/카드값이 없는 빈 요청1회로 연결을 확인했다. HTTP401/UNAUTHENTICATED와 localhost5173 CORS응답은 소스의 필수입력검증 거절과 일치한다. 카드조회/잠금횟수증가 경로 전 거절이므로 실제학생 상태를 바꾸지 않았다. 이를 정상학생 로그인성공이라고 보고하지 않는다.
- cloud Vite빌드·웹 tsc·diff검사 통과. 기존큰청크경고 유지. 실제카드로그인 성공은 사용자의 재시도 결과를 기다리는 상태이며 미확인이다.
