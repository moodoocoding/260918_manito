- 날짜: 2026-10-30. 수행 주체: 이 채팅 Codex 한 에이전트의 6개 가상 역할 검토. 외부 전문가 참여 없음.

- 대상: 개발 `manito-938cc`, 서울. 신규 `getStudentBalanceGame`, `submitBalanceGameChoices`, `retryStudentBalanceMatching` 3개만 선택 배포. 기존 함수 59개와 Supabase·Vercel·Firestore 인덱스는 배포 대상에서 제외한다.
- 입력 자료: AGENTS/6개 전문가 프로파일, 기존 `2026-10-30-class-balance-game.md`와 `2026-10-30-community-world-unification.md`, 함수 소스/API/스키마, 개발 서버 함수·규칙 메타데이터의 읽기 전용 비교.

- 규칙 차이: 기존 모든 경로·헬퍼·권한은 동일하다. 신규 `balanceGamePublic/progress`에만 현재 자격을 가진 회차 참가자 읽기를 추가하고, 신규 비밀 답변/짝 정보와 교사 편지 경로의 직접 접근 거부를 명시한다(이 경로들은 기존 포괄 거부 상태). 새로운 쓰기 권한은 없다.
- 사용자 과업·섹션·상태·반응형은 앞선 두 화면 검토와 동일하다. 이번 범위는 해당 코드의 배포와 서버 권한 확인이며 화면을 다시 설계하지 않는다.

## 배포 전 발견과 수정 설계 재검토

- D1·P1: 신규 함수의 초기 상태 검사는 `active` 여부만 확인하고 `endsAt`을 검사하지 않는다. 또한 제출 전 검사와 저장 사이, AI 요청과 최종 저장 사이에 회차 일시정지/종료·명단 철회가 생기면 재확인하지 않는다. H5(실수/잘못된 제출 예방)와 서버 시간·제출 제한 계약에 따라 배포 전에 보강한다.
- 수정 설계: 기존 `assertStudentTransaction`을 그대로 재사용하고 신규 모듈 내부에서 서버 시간/회차·명단 버전을 트랜잭션으로 확인한다. 최초 상태 생성·선택 저장·재시도에서 본인 자격과 참가 상태를 확인한다. AI 결과 저장 직전에는 학급·현재 회차·종료 시각·고정 명단 버전과 모든 참가자의 철회/차단 상태를 다시 확인한다. 실패 시 결과를 공개하지 않고 기존 실패 상태/재시도 안내를 사용한다. 기존 다른 함수·공통 도우미는 수정하지 않는다.

## 배포 직전 검증·D1 조치 결과

- 신규 모듈에서 기존 `assertStudentTransaction`을 재사용해 종료 시각/회차/명단·카드 자격을 저장 트랜잭션에 묶었다. AI 결과 확정 전에도 회차/전체 명단 상태를 확인한다. 기존 공통 도우미와 다른 함수는 수정하지 않았다.
- 단위22/22, Rules15/15 통과. 보강 후 전체 통합 실행에서 기존11개는 통과했고 신규2개의 가상 회차 ID가 기존10자 검증보다 짧아 실패했다. 서비스 검증을 완화하지 않고 fixture ID를 고쳐 자리바꾸기10/10을 재실행·통과했다(기존 통합11+자리바꾸기10의 확인 결과).
- 최초 root build는 다른 채팅의 main.tsx TS2367에서 중단됐다. 담당 채팅에 전달했고 수정 후 이 채팅에서 웹 TypeScript/Vite 빌드 성공을 다시 확인했다. Functions TypeScript도 통과했다. 기존 큰 JS 청크 경고가 남는다.
- Emulator 실행은 로컬 Node24를 사용했고 실제 배포 runtime은 Node22다. 로컬 기능/권한 통합과 클라우드 runtime 확인을 구분한다. 실제 학생/모델 호출은 하지 않았다.
- D1: 만료·일시정지·명단버전 변경·철회·차단 후 결과 미공개, 중복 제출·본인 외 답변 차단·구카드 차단을 확인해 해결했다. 6개 관점에서 앞선 수정 설계의 근거가 유효하며 새 UI 변경은 없다. 배포 전 미해결 P0·P1 없음.
- 현재 규칙 대비 추가30줄/기존 줄 수정·삭제0임을 자동 비교했다. 전역/기존 함수 배포 없이 신규3함수와 Firestore Rules만 선택한다.

## 배포·사후 확인

- 개발 `manito-938cc`에 `getStudentBalanceGame`, `submitBalanceGameChoices`, `retryStudentBalanceMatching` 3개와 `firestore:rules`만 선택 배포했다. CLI의 성공 생성3건/Deploy complete를 확인했다. 실제 Cloud Functions runtime은 모두 `nodejs22`, 서울, 상태 `ACTIVE`다.
- 함수 수59→62. 기존59개 각각의 수정 시각·리비전·runtime·URL·Secret 참조·labels를 배포 전후 자동 비교해 동일함을 확인했다. 이 작업에서 기존 함수의 코드를 배포하거나 덮어쓰지 않았다.
- 새 제출·재시도 두 함수에 `GEMINI_API_KEY` 버전1 연결과 실행 계정의 해당 Secret 읽기 권한이 설정됐다. 키 값은 읽거나 출력하지 않았다. 기존 Secret/다른 함수 환경값은 변경하지 않았다.
- 배포된 Rules 원문 SHA256이 저장소 파일과 일치한다. 기존 규칙 줄의 수정/삭제0·새 경로 추가30줄이다. 인덱스는 배포하지 않았다.
- 새3함수의 실제 클라우드 URL로 합성 회차ID만 넣은 비인증 POST를 보내 모두 HTTP403/PERMISSION_DENIED를 확인했다. 인증 경계 앞에서 종료되어 실제 학급/학생 기록과 Gemini를 사용하지 않았다.
- 증거: [배포 검증 JSON](assets/balance-deployment-verification-2026-10-30.json). 실제 학생/인증된 브라우저 전체 흐름·Gemini 키의 API 유효성/모델 응답·짝 품질은 미확인이다. 서버에 Secret이 연결됐다는 사실과 실제 AI 성공을 구분한다.
