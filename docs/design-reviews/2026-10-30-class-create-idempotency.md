# 전문가 검토 기록: 자동 학급 코드 생성 요청의 멱등 재시도 복구

## 검토 정보

- 날짜: 2026-10-30. 수행: `/root/teacher_mail_backend`의 여섯 가상 프로파일별 역할 검토, 실제 전체 통합 재실행은 부모 `/root` 담당. 외부 전문가 참여 없음.
- 발견: 전체 에뮬레이터에서 새 교사 우체통과 두 시즌 흐름은 통과했지만 기존 학급 생성 시험의 동일 요청 재시도가 `already-exists`로 실패했다.
- 입력: `createClass.ts`, `shared/idempotency.ts`, `auth/codes.ts`, `tests/functions.integration.test.mjs`, API 문서의 멱등 요청 계약과 전문가 운영 지침/여섯 프로파일.
- 범위: `createClass` fingerprint의 학급 코드 한 항목을 생성 결과 대신 정규화된 사용자 입력 의도로 바꾼다. 같은 요청ID의 동시 자동 생성·재시도 시험을 강화한다. UI·권한·랜덤 코드 형식·실제 저장 결과·다른 함수는 변경하지 않는다.

## 요구사항·사용자 과업·주요 상태·화면 영향

- 교사는 학급 생성 응답이 늦거나 소실돼 같은 요청을 다시 보내도 같은 학급/코드를 받아야 한다. 동일 요청ID에 다른 이름 등 다른 의도는 계속 거절한다.
- 현재 문제: 자동 코드 난수를 매 호출 새로 생성하고 이 결과를 입력 fingerprint에 넣어, 같은 의도라도 매번 다른 요청으로 오해한다. 트랜잭션 안/앞의 동일 명령 확인 양쪽에 영향을 준다.
- 설계: fingerprint의 `{classCode: requestedCode}`로 자동 생성은 빈 문자열, 사용자 지정은 정규화된 입력값을 해시한다. 생성된 최종 `classCode`는 `result`와 실제 학급 코드 문서에 그대로 기록한다.
- 호환: 사용자 지정은 원래 `classCode === requestedCode`여서 기존 fingerprint와 동일하다. 이전 자동 명령은 임의 생성값을 해시했으므로 새 빈 입력 해시와 자동 변환하지 않는다. 이 기록의 과거 요청 재시도는 이미 실패하던 범위이며 이번 한 줄 수정으로 과거 명령 복구를 주장하지 않는다.
- 상태: 첫 요청/동일 의도 동시 요청/동일 의도 재시도 → 같은 확정 결과. 다른 의도 요청ID 재사용 → 기존 `already-exists`. 코드 중복/권한 오류도 기존 동작 유지.
- 페이지/섹션·반응형·긴 문장·최대 목록·키보드/초점: 변경하지 않는 서버 명령 식별 수정으로 직접 영향 없음. 새 입력·문구·조작·저장 상태는 추가하지 않는다.

## 구현 후 검토

- 구현: fingerprint 한 항목만 `{classCode: requestedCode}`로 바꿨고 실제 코드 생성/반환/저장·교사 권한·트랜잭션·명령 검사는 유지했다.
- 검증: `npm --workspace functions test` 통과(빌드/현재 단위22개, 병행 작업의 추가 시험 포함), `node --check tests/functions.integration.test.mjs`·`git diff --check` 통과. 통합 시험은 초기 자동 생성2개를 동시에 보내 같은 결과와 학급 수1을 검사하고 기존 순차 재시도/이름 변경 충돌 검사도 유지한다.
- 실제 검증: 부모 `/root`가 JDK21을 명시해 실행한 전체 `tests/*.integration.test.mjs`가 11/11 통과(65.7초). 자동 학급 생성의 동시/순차 재시도·이름 변경 충돌을 포함한다. Firestore Rules도 14/14 통과했다. 기존 기능의 필수 불변 조건을 복구한 것으로 새 UI 범위의 확장을 뜻하지 않는다.
