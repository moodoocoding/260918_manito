# 전문가 검토 기록: 실제 자리바꾸기 질문 미표시 복구

## 요구사항·관찰·범위

- 2026-10-30 사용자가 실제 `http://127.0.0.1:5175/student/community`에서 자리바꾸기에 질문이 없다고 보고하고 화면을 첨부했다. 단위/가상 미리보기/비인증 서버 거부 검증을 실제 학생의 질문 표시 성공으로 확대하지 않는다.
- 관찰: `getStudentBalanceGame` 오류 후 질문과 참가 수는 없는데도0명/아직 완료한 친구 없음으로 표시한다. Firebase SDK의 `error.code`를 읽지 않고 `message`에서 코드를 검색해 실제 `failed-precondition` 이유를 일반 오류로 숨긴다.
- 조사 중: 마니또 진행·종료 시각·명단 조건과 게시판의 실제 이용 조건 충돌 가능성. 정확한 서버 거절 이유 확인 전 자격·회차 안전 검사를 임의로 없애지 않는다. 기존 Supabase·기존 함수·학생 카드/데이터는 변경하지 않는다.
- 수행: 이 채팅 Codex 한 에이전트의 가상6프로파일. 운영 지침/6프로파일, 공통 디자인 기준, 기존 자리바꾸기 검토와 코드·사용자 캡처를 읽었다. 실제 외부 전문가 참여 없음.
- 화면 구조는 공통 헤더 → 안내/현재 질문 또는 원인이 있는 오류 → 실제로 조회된 완료 현황이다. 한 질문씩 총10개 선택 흐름은 유지한다.
- 상태: 조회 중/조회 실패에서는 인원과 완료자 부재를 단정하지 않는다. 오류 코드에 맞는 안전한 학생 안내와 재시도를 제공하고, 내부 오류의 임의 원문·ID를 출력하지 않는다. 저장 실패의 오류를 재조회가 지우지 않도록 별도 확인한다.
- 반응형/키보드: 공통1200/860px·768이하한열·큰 라디오/CTA·제목/질문/복귀 초점 유지. 실제5175의 고정 cloud 빌드 갱신과 질문 표시를 확인하며 입력 중 HMR 재시작을 피한다.

## 근본 원인과 수정 설계 재검토

- 학생/명부/응답을 읽지 않고 개발 학급4개의 회차 상태·끝난 시각만 확인했다. 학생 홈이 선택하는 회차는 모두 종료 시각 경과 상태였다(공개 대기1·보관1·상태만 진행 중2). 사용자5175 캡처의 질문 없음과 코드의 `roundIsOpen` 거절이 일치한다. 기존 마니또 기간을 자리바꾸기 이용조건으로 결합한 설계가 원인이다.
- 원래 학급 월드의 별도 게시판 기능에 맞춰 새3함수와 데이터만 학급별 자리바꾸기 활동으로 분리한다. 기존 `requireActiveStudent`/`assertStudentTransaction(..., requireActiveRound=false)`를 재사용한다. 기존 마니또 회차 날짜·상태·배정·학생 카드, 기존 함수·Supabase는 변경하지 않는다.
- 새 경로: `classes/{classId}/balanceGameSecrets/current`와 그 `submissions/{uid}`(서버 전용), `classes/{classId}/balanceGamePublic/progress`(그 활동의 활성 학급 참가자만 읽기). 이전 round 아래 기록은 이동·복사·삭제하지 않는다. 기존class 문서의 설정/회차 필드도 바꾸지 않는다.
- 첫 조회 시 활성 학급 명부를 서버에서 고정한다. 2~40명 짝수일 때 제출/전원매칭이 가능하다. 인원 부족·홀수·시작 후 명부 변경은 질문10개 탐색과 이유 안내를 제공하되 제출/AI 확정은 막는다. 무단 제외·새 짝 덮어쓰기·학생의 명부 조회는 허용하지 않는다.
- 질문은 회차가 없거나 끝난 학급에서도 본인 카드 자격 검증 뒤 반환한다. 마니또 회차가 없는 학생도 게시판에 들어갈 수 있도록 main의 게시판 진입 조건만 조정한다. 기존 교사 안내는 회차가 있을 때 기존 함수를 그대로 사용하고 없으면 기본 배려 아이디어를 제공한다.
- 응답: `gameId`, `canSubmit`, `availabilityMessage`, 준비 불가 시 `progress:null`을 명시한다. 구 클라이언트의 `roundId` 입력은 인증/범위 결정에 사용하지 않으며 학급은 검증한 토큰으로만 정한다. 전원 선택·실시간 완료·본인짝·가명AI·단일시도 잠금·실패재시도는 유지한다. 명부/카드 차단은 저장과 AI 확정 트랜잭션에서 재검사한다.
- 첫 독립 활동은 학급별1개 고정 세션이다. 교사의 다음 자리바꾸기 생성/초기화 UI는 이번 최초 기능 범위 밖이며 이미 저장된 선택·짝을 자동 초기화하지 않는다.
