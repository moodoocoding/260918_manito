기준일2026-10-30. 사용자가 명시한 제품 계층이며 신규 화면·API·데이터 설계보다 먼저 적용한다.

마을 제목/로그인/기본 학급 관리에 ‘마니또 시즌2’ 같은 특정 서비스 상태를 올리지 않는다. 각 서비스의 기간 종료가 다른 서비스의 종료를 뜻하지 않는다. 메인 건물의 ‘마니또’는 오늘 할 일·우체통·게시판과 나란한 한 진입점이다.

## 기존 DB와 API를 계승하는 방식

- 기존 개발 Firebase `manito-938cc`와 교사 UID, `classes/{classId}`, 학생 명부·로그인 자격·카드/학급 코드, 기존 마니또 `rounds` 및 기록을 그대로 사용한다. 제품명/화면 계층 변경은 데이터 이사나 카드 재발급을 요구하지 않는다.
- 기존 `getStudentHome`은 class/member/sessionVersion을 확인하고 optional `round`를 반환한다. 해당 필드는 기존 마니또 문맥이지 공통 서비스 가동 상태가 아니다. 공통 접근을 round로 제한하지 않는다.
- 당장 모든 함수/경로를 이름 바꾸지 않는다. 기존 계약과 데이터가 안전하게 계속 작동하는 것이 우선이다. ‘플랫폼 분리’를 이유로 인증/학급을 이중 생성하지 않는다.
- 새 학급 기능은 자체 경로·상태를 설계한다. 기존 round 밑의 같은 종류 기록이 있다면 보존하며 전환/조회 정책을 명시하고 자동 삭제·덮어쓰기를 하지 않는다.
- 교사 서비스 모음의 표시 상태와 실제 학생 사용 설정/권한을 구분한다. 단순 카탈로그 카드 추가가 서버 연결·운영 설정 완료를 뜻하지 않는다.
- 선생님 방은 사용자가 지정한 목재 허브 안에서 학급 선택/개설·명부/코드/카드 공통 관리와 여러 서비스의 현황/운영 진입을 한곳에서 조율한다. 마니또는 그중 한 서비스다. 승인된 허브 구조를 유지하면서 실제 가능한 관리 행동을 연결하고, 서버 계약 없는 전체 서비스 제어 기능을 완성된 것으로 표시하지 않는다.

## 새 기능의 필수 설계 질문

1. 공통 학급 기능인가, 특정 서비스의 내부 기능인가?
2. 소속/자격 검증과 그 서비스의 실행 조건이 구분되는가? 다른 서비스의 round/status를 불필요하게 가져오지 않는가?
3. 어떤 명부와 상태를 사용하는가? 조회/질문 탐색·제출·결과 공개 조건은 무엇인가?
4. 기존 데이터는 어디에 그대로 남고, 새 기능은 어떤 경로/API를 추가하는가?
5. 마을 복귀·종료·실패/재시도·공용기기 정리를 공통 방식으로 제공하는가?

- 선생님 방 담당: 공통 학급 관리와 서비스 모음을 분리하고 교사 Google 인증/화면 검증을 보강한다. 기존 학급을 재사용한다.
